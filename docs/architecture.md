# Architecture

`index.html` loads the browser-ready `dist/app.bundle.js` build. Its source entry point is `src/app.js`, which imports the runtime coordinator in `src/main.js`; configuration, streaming-response cleanup, chat title/memory helpers, storage identifiers, and DOM identifiers are maintained in focused modules under `src/config`, `src/api`, `src/core`, `src/ui`, and `src/utils`.

The browser UI persists chats in IndexedDB and both the completed-chat counter and pending-ad requirement in localStorage. AI requests are sent directly to ten Dahl providers in order. Each provider tries DeepSeek first, GLM 5.3 second, and MiniMax M2.7 third before the app moves to the next provider. Text and source-code attachments are read in the browser and included as text context; the available Dahl models reject image input, so image, PDF and DOCX upload is not exposed. The API helper layer handles cumulative chunks and prevents repeated rendered blocks. There is no token limit: after every two complete chat cycles (one user message plus one successful AI reply per cycle), Adsterra Native Banner zone 31570743 is inserted inline between chat messages. The composer remains disabled until the user manually clicks Close after its 0.5-second delay. A pending ad survives refresh and is propagated to other tabs. Only a confirmed Native Banner script request error triggers the blocker warning; an empty creative container can mean normal no-fill and no longer causes a false blocker result. No full-screen ad overlay is used. The separate Social Bar placement remains enabled for Adsterra’s notification-style ads. Because this is a static frontend, API keys and client-side enforcement logic remain visible to visitors.
